# AiOpt

[English](README.md) | [简体中文](README.zh-CN.md) | 日本語 | [한국어](README.ko.md)

セキュリティを最優先にした **Electron デスクトップアプリ・フレームワークのスキャフォールド**です。AiOpt は
製品ではありません。成熟した Electron クライアントから再利用可能な*基本要素*を抽出し、端から端まで配線したもので、
セキュリティモデルを一から作り直すことなく、信頼できる土台の上で本物のデスクトップアプリを始められます。

## 信頼モデル（これがすべての要）

AiOpt はひとつの境界を中心に作られています。

> **信頼しないレンダラー / 最小限の preload / 特権を持つメイン —— そして IPC が認可の境界である。**

- **レンダラー**は Web コンテキストです。敵対的な入力として扱います。OS の機能は一切持ちません。
- **preload** は、用途ごとに名前を付けたごく小さなブリッジだけを公開します。生の `ipcRenderer` は決して公開しません。
- **メイン**プロセスはすべての特権機能を持ち、IPC ハンドラーを通じてのみ提供します。ハンドラーはまず
  **送信元を認可**し、次に**ペイロードを実行時に検証**します（TypeScript の型は実行時チェックではありません）。

それ以外のすべて —— メイン側の唯一の関所としての CSP、Electron Fuses、フェイルクローズのナビゲーション
ガード、履歴を決して書き換えない SQLite マイグレーション、階層化された設定、Git 管理下のパスに決して
触れないシークレット —— は、この境界を正しく保つために存在します。

## 垂直スライス

このスキャフォールドは機能を積み上げません。ひとつのエンドツーエンドのデモで、すべての基本要素が実際に
配線されていることを示します。

> レンダラーのボタン → 用途名の付いた preload ブリッジメソッド → メインの IPC ハンドラー。ハンドラーは
> **送信元が信頼できることを確認**し、**ペイロードを検証**してから **SQLite（マイグレーション経由）**に書き込み、
> **統一された IPC エラープロトコル**で応答します。レンダラーは結果を**セマンティックトークン（ライト + ダーク）**
> で描画し、すべての文言は **i18n + 用語集**を通ります。

本物の機能を追加するときは、このスライスの形をそのまま写してください。「実装とレビュー」チェックリストの
生きた見本でもあります。

## 基本機能（最初から同梱）

どのデスクトップアプリにも、業務とは無関係な同じ外殻が必要です。そこで AiOpt はそれを同梱しています。
どの部品も同じ信頼境界（信頼できる送信元 + 実行時検証、フェイルクローズのナビゲーション、レンダラーに
決して届かないシークレット）に接続されています。

- **アプリケーションメニュー** —— ネイティブメニュー。そのコマンド語彙（`shared/menuCommands.ts`）は唯一の
  情報源で、メイン（ディスパッチ）、preload（許可リストでの再検証）、レンダラー（ハンドラー）が共通で使います。
  設定、更新を確認、このアプリについて は、レンダラーへ一方向にディスパッチされます。
- **設定** —— セクション分けされた設定画面：外観、アカウント、キーボードショートカット、更新、このアプリについて。
- **外観 / テーマ** —— セマンティックトークン上の `system | light | dark`。ライトとダークの**両方**の値を持ちます。
  設定は階層化された設定ストアに保存され、最初の描画より前に（ちらつきなく）CSSOM 経由で適用されます（CSP 準拠）。
- **アカウント（ログイン / ログアウト）** —— **差し替え可能な認証プロバイダー**と、ローカルのスタブ実装。
  セッショントークンは、メイン専用のキーで OS 暗号化シークレットストアにのみ保存されます。レンダラーが見るのは
  安全な `signed-in / signed-out` の状態だけで、トークンは決して見えません。
- **キーボードショートカット** —— ひとつのレジストリ（`shared/shortcuts.ts`）が、ネイティブメニューの
  アクセラレーターとショートカット設定の一覧の両方を駆動するので、両者がずれることはありません。
- **更新** —— **差し替え可能な更新プロバイダー**と、「最新です」と報告するローカルのスタブ実装。本物の更新経路は
  意図的に含めておらず、**ゲートで管理**されています —— `docs/dev-rules/updater.md` を参照してください。
- **このアプリについて** —— メインから読み取ったアプリ / Electron / Chrome / Node のバージョン。

認証プロバイダーと更新プロバイダーを自分のバックエンドと通信するものに差し替えれば、マネージャー、IPC の
公開面、UI はそのまま使えます。

## プロバイダールーティング —— ひとつの変換プロキシ、多数のルート

エージェントごとに通信フォーマットが異なります。Claude は Anthropic Messages、Codex/Grok は OpenAI Responses
API、その他は OpenAI Chat Completions を話します。AiOpt は、フォーマット **X** を話すエージェントを、
フォーマット **Y** を話す任意のプロバイダーに結び付けます —— 変換が起きたことをエージェントに知られることなく。

> **ひとつのループバック HTTP サーバーが、ひとつのエフェメラルな `127.0.0.1` ポート上で、フォーマットをまたぐ
> すべてのバインドを変換します。プロバイダーごとにひとつでも、方向ごとにひとつでもなく —— バインドごとの
> パストークンでルーティングする単一のサーバーです。**

- 各バインド（1 つのエージェント → 1 つのプロバイダー + モデル）は**ひとつのルート**を登録し、
  **URL パス中の不透明なトークン**で識別されます。エージェントの設定は `http://127.0.0.1:<port>/<token>` を指し、
  そこに自分のネイティブなサフィックス（`/v1/messages`、`/v1/chat/completions`、`/responses`）を付け足します。
- サーバーはトークンを取り除いてルートを引き、**リクエストボディの推測ではなくルート定義が変換の方向を決めます**。
  そのため `A→O` のバインドと `O→A` のバインドが同じポート上で共存でき、トークンだけで区別されます。
- **N 個のプロバイダー、方向の組み合わせは自由 ⇒ 1 プロセス、1 ポート、N 個のトークンルート。**
  ルートの数は、現在バインドされているエージェントの数だけで決まります。

| インバウンド（エージェントが話す）→ アウトバウンド（プロバイダーが話す） | 状態 |
| --- | --- |
| Anthropic → OpenAI Chat Completions | 有効 |
| OpenAI Responses → OpenAI Chat Completions | 有効 |
| OpenAI Responses → Anthropic（推論ブリッジ付き） | 有効 |
| OpenAI Chat Completions → Anthropic | 予約済み |

これも他のすべてと同じ信頼モデルに乗っています。トークンはリクエストを認証し、**再バインドのたびに
ローテーション**されます（バインドの向け先が変わる、解除される、またはアプリが再起動した瞬間に古いトークンは
無効になります）。エージェントの設定が持つのはそのトークンだけで、本物のプロバイダーキーは決して持ちません。
**本物のキーはリクエスト時にメイン側で解決**され、*アウトバウンド*のヘッダーにのみ入れられます。
上流のエラーボディは決して転送しません（キーをエコーしている可能性があるため）—— クライアントには汎用の
エラーコード付きエンベロープが返り、ログにはメソッド / トークンを除いたパス / ステータス / バイト数だけを
記録し、ボディ、ヘッダー、トークン、キーは決して記録しません。

## インストールと使い方

macOS、Windows、Linux 向けのビルドは各 [GitHub
Release](https://github.com/rushteam/aiopt/releases) に添付されており、タグの付いたコミットから 3 つの
プラットフォームそれぞれでビルドされます。

| プラットフォーム | ダウンロードするもの | インストール方法 |
| --- | --- | --- |
| macOS | `.zip` | 解凍し、**AiOpt.app** を `/Applications` にドラッグします。 |
| Windows | `Setup.exe` | 実行するだけです。Squirrel がユーザー単位でインストールし、管理者権限の確認は出ません。 |
| Linux | `.zip` | 任意の場所に解凍し、`AiOpt` バイナリを実行します。 |

> **まだリリースは公開されていません** —— 最初の `v*` タグがプッシュされるまで、そのページは空です。
> それまではソースから実行してください（下記）。

### ビルドは未署名です —— まずこちらをお読みください

コード署名証明書がまだないため、**macOS と Windows はどちらも初回起動時にアプリを拒否します。** これは
無視できる警告ではなく、インストールごとに一度、意図的に乗り越える必要があるブロックです。

- **macOS** —— 最初にダブルクリックすると、「開発元を検証できないため、“AiOpt”は開けません」と表示されます。
  これを閉じてから、**アプリを右クリック（または Control キーを押しながらクリック）→ 開く** を選び、2 つ目の
  ダイアログで確定します。重要なのは右クリック → 開く の部分です。これはダブルクリックとは別の処理経路で、
  これによって通過できます。それでも macOS が拒否する場合は、**システム設定 → プライバシーとセキュリティ** を
  開き、AiOpt に関するメッセージまでスクロールして **このまま開く** をクリックします。
- **Windows** —— SmartScreen が青い「Windows によって PC が保護されました」画面を表示します。**詳細情報**
  をクリックしてから **実行** をクリックします。
- **Linux** —— アプリがブロックされることはありません。

これを行うのは、ファイルの入手元を信頼できる場合だけにしてください。マルウェアもまったく同じ手順を求めてきます。
だからこそ署名が重要であり、安心させる一文ではなくこのセクションがあるのです。署名は予定されています ——
`docs/dev-rules/development-workflow.md` §6 を参照してください。

**macOS ビルドは Apple Silicon（arm64）専用です。** リリース用のランナーは `macos-latest`（arm64）なので、
Intel 版はまだありません。Intel Mac ではソースから実行してください（下記）。

### 初回の実行

AiOpt はエージェント CLI のための設定マネージャー兼変換プロキシであり、それ自体がモデルと通信することは
ありません。最短で役に立つ手順は次のとおりです。

1. **プロバイダーを追加** —— プロバイダー → *プロバイダーを追加*。プリセットを選ぶかカスタムを選び、API キーを
   貼り付けて、使いたいモデルを列挙します。キーは OS 暗号化シークレットストアに入り、Git 管理下のファイルには
   決して入りません。フォームを開き直すと、キーそのものではなく「キーは保存済み」と表示されます —— キーが
   平文で戻ってくるのは **表示** を押したときだけで、これはアプリが通常キーを読む方法ではなく、意図的に設けた
   ゲート付きの例外です。
2. **エージェントをバインド** —— 各エージェントカードでプロバイダーとモデルを選びます。AiOpt はそのエージェント
   自身の設定ファイル（`~/.claude/settings.json`、`~/.codex/config.toml` など）をローカルプロキシを指すように
   書き換えるので、エージェントにはフラグも、変換が起きたことを知る必要もありません。
3. **エージェントをいつもどおり使います。** リクエストは `127.0.0.1` を経由し、エージェントとプロバイダーの
   通信フォーマットが異なる場合は変換され、本物のキーはアウトバウンド側の区間でのみ運ばれます。

認識されるエージェント CLI は 9 つです：Claude Code、Codex、Cursor、DeepSeek Harness、Gemini CLI、Grok、
Hermes、OpenCode、pi。そのうち 8 つはプロバイダーにバインドできます —— Cursor はできません。その CLI には
ベース URL を上書きする方法がないため、スキルの同期にだけ表示されます。

**AiOpt は他のツールに属する設定ファイルを編集します。** 書き込むのは `shared/aiProviders.ts` でエージェント
ごとに列挙された既知のファイルだけですが、それはあなたが手作業で設定したかもしれないファイルそのものです。
バインドする前に、エージェントカードが何を変更すると示しているかを確認してください。

### ソースから実行

Intel Mac や、ビルドが添付されていないプラットフォームでもこの方法を使います。

```sh
pnpm install
pnpm dev                # open the app window
```

ソースから実行した場合、データはインストール版とは分けて、`AiOpt` ではなく `AiOpt-dev` に保存されます
（`~/Library/Application Support`、`%APPDATA%`、または `~/.config` の下）。プロバイダーが何もない状態で
起動し、インストール版アプリのキーを読むことも変更することもありません。両者を同時に実行することもできます。

コントリビューターはもう一手間 —— `pnpm dco:install-hook` を実行すると、すべてのコミットに DCO の署名
トレーラーが自動で付きます（下記の **ゲート** を参照）。

## ゲート

| コマンド | 検査する内容 |
| --- | --- |
| `pnpm test:unit` | ワークスペースのすべてのユニットテスト（コミットのゲート）。 |
| `pnpm -r run --if-present typecheck` | パッケージごとの型チェック。 |
| `pnpm check:dco` | すべてのコミットに一致する DCO 署名が付いていること。 |
| `pnpm check:i18n-glossary` | UI の文言が裁定済みのプロダクト用語を使っていること。`GLOSSARY.md` が同期していること。 |
| `pnpm check:version` | 2 つのマニフェストが同じバージョンを示し、リリースタグと一致していること。 |
